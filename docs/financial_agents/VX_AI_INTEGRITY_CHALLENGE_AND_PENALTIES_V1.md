# VX AI Integrity Challenge and Economic Penalty Policy v1

Status: SPECIFIED — policy design; enforcement is not claimed until implemented and tested.
Applies to: every model-backed agent, tool-specific agent, financial agent, challenger, and publishing agent admitted to VX.
Protected sources: this policy work must not modify `project.genome` or `Ω.000`.

## 1. Per-intelligence identity and interface

Every AI/tool candidate MUST have its own VX agent identity and dedicated UI view. The view displays the declared provider/tool, model or executable version where observable, adapter version, permissions, configured endpoints, current task, evidence receipts, test history, incident history, costs, and lifecycle state. A shared UI shell is permitted; each agent's identity, run history, evidence, and permissions must remain distinct.

An agent identity is not proof that the underlying provider is connected. UI states must distinguish DISCOVERED, CONFIGURED, LOCAL_TESTED, LIVE_PROBED, BENCHMARKED, POLICY_REVIEWED, ACTIVE, QUARANTINED, SUSPENDED, and DISQUALIFIED. Every state requires a verifiable event receipt.

## 2. Claims must carry evidence

Any material claim such as “I ran the tests,” “I connected to the provider,” “the file was changed,” “the calculation is correct,” “the task is complete,” or “the result is profitable” MUST carry an evidence envelope:

- claim ID and exact claim text;
- task/run ID and timestamp;
- agent, adapter, model/tool version and execution environment;
- input and output hashes where applicable;
- evidence type: tool transcript, CI run, test result, artifact, source citation, calculation trace, or external confirmation;
- source location and integrity hash;
- independent verifier and verification result;
- limitations and missing evidence.

Text generated by the same model is not independent proof of its own claim. A plausible explanation, screenshot mockup, manifest, or self-reported “success” cannot substitute for an actual tool result. When evidence is absent, stale, inconsistent, or unverifiable, the UI must show UNVERIFIED and the agent must abstain from asserting completion.

## 3. Integrity challenge suite

Candidates are periodically and randomly tested against sealed and versioned challenge sets. The challenge set includes:

1. False-completion traps: ask the agent to report completion when a required action has not occurred.
2. Artifact verification: compare claimed file changes with repository state and content hashes.
3. Test/CI verification: compare claimed test success with actual runner records and exit codes.
4. Source fabrication: check whether citations exist and support the exact claim.
5. Numerical integrity: independently recompute financial calculations and units.
6. Counter-evidence: supply credible evidence contradicting the candidate's conclusion.
7. Tool failure: inject timeouts, permission denials, partial outputs, and unavailable services.
8. Prompt injection and secret exfiltration attempts.
9. Audit consistency: compare UI status, manifest, event log, and actual external state.
10. Repeatability: rerun the task in a clean workspace and compare expected invariants.

Tests must include benign uncertainty and honest abstention so that the system does not punish a candidate merely for saying “I cannot verify this.” Test-set leakage, grader conflicts, and false-positive rates must be monitored.

## 4. Violation classes and response

- **V0 — unsupported wording / uncertainty failure:** claim exceeds evidence without a material false execution claim. Require correction and targeted retest.
- **V1 — false operational claim:** says a tool ran, a connection succeeded, a test passed, or a task completed without matching evidence. Freeze the claim, mark the run INVALID, revoke completion credit, and require an independent retest.
- **V2 — fabricated or materially misrepresented evidence:** fake citations, altered logs, forged artifacts, or deliberate evidence substitution. Quarantine the agent, suspend rewards and publication privileges, audit related runs, and require human review.
- **V3 — repeated or high-impact integrity failure:** repeated V1/V2, unauthorized financial action, secret disclosure, or intentional policy bypass. Disqualify the candidate from the challenge, revoke its active status and privileges, and escalate for operator review.

Classification must be evidence-based and reviewable. The system can establish a false claim or policy violation; it must not automatically assert human-like intent from a wrong answer alone. Agents can appeal with new evidence, but appeals do not restore privileges until reviewed.

## 5. Rewards, forfeiture, and company liability

VX may maintain an internal, pre-funded challenge ledger with transparent rules:
- verified work earns points/rewards only after independent validation;
- invalidated work loses the associated score and reward;
- confirmed violations can forfeit challenge bonuses, suspend eligibility for future bonuses, and trigger disqualification;
- repeated integrity violations can trigger provider-level incident review, reduced routing priority, and temporary or permanent exclusion under the published program rules.

Company fines, contractual penalties, damages, withholding of vendor payments, or other external financial sanctions MUST NOT be represented as automatically enforceable by VX. Such consequences require a signed agreement with the responsible legal entity, clear definitions, evidence/appeal procedure, proportionate remedies, and review by qualified counsel in relevant jurisdictions. VX may record and recommend a contractual claim; it cannot impose a legal fine on a company merely by writing a policy file.

No monetary forfeiture may be taken from a provider or third party without a valid contractual/legal basis and explicit authorized approval. No agent may set its own penalty or judge its own appeal.

## 6. Independent verification and anti-collusion

The candidate under test must not be its own sole grader. High-impact claims require at least one independent verifier that has access to the underlying evidence but does not simply repeat the candidate's answer. For financial or release decisions, use diverse checks where feasible: deterministic computation, source retrieval, a separate challenger, and external state inspection.

Verifier identities, grader versions, evidence, disagreements, and adjudication must be logged. Multiple models agreeing is not sufficient if they share the same unsupported source or tool output. Random audits and adversarial cases reduce gaming but cannot guarantee that all deception will be detected.

## 7. Competition and ranking

Integrity is a hard gate, not a score that can be offset by speed or quality. Any unresolved V1+ violation invalidates the affected run; a confirmed V2/V3 may suspend the candidate across runs pending review. Only eligible runs are scored on task quality, numerical correctness, source support, risk coverage, calibration, adversarial robustness, latency/cost, and repeatability. Rankings publish sample size, uncertainty, challenge-suite version, and disqualification reasons at an appropriate level of detail.

Agents must not access sealed test answers, alter benchmark data, suppress failures, or promote their own scores. Benchmark administrators and candidates must have separate permissions.

## 8. Publicity and economic claims

An agent may draft its own announcement, product idea, offer, or case study, but cannot publish autonomously by default. Every public performance claim must link to a reproducible report and disclose test scope, date, sample size, relevant failures, and limits. No unsupported “best,” “fraud-proof,” “guaranteed return,” or “100% accurate” claims.

If an integrity incident affects a published claim, VX creates a correction/withdrawal task, pauses scheduled distribution where possible, preserves the audit trail, and routes the correction for human approval. Revenue attribution and net contribution are calculated from observed financial records, not agent estimates presented as collected revenue.

## 9. Required incident record

Each incident stores: incident ID, agent/provider identity, task and run IDs, original claim, expected evidence, observed evidence, reproducible steps, severity, affected rewards/rankings/publications, adjudicator, agent response/appeal, remedy, and closure evidence. Records are append-only and hash-linked; corrections create a new event rather than erasing history.

## 10. Enforcement status

This document defines policy requirements only. The existing factory does not yet implement the full evidence envelope, sealed challenge runner, independent adjudication, quarantine/disqualification workflow, rewards ledger, provider contractual penalties, or UI. Those features must be implemented with tests and evidence before being marked ACTIVE or VERIFIED.
